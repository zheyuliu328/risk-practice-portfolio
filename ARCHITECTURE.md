# Portfolio architecture and editorial rules

The portfolio is an evidence-led presentation and learning system. It is not one universal risk application. The visitor should find a problem they understand, inspect a result, reproduce it and see what the result does not justify.

## What is shared

- Navigation from task to evidence and learning prerequisites.
- Review contract: inputs/units/time, method, independent challenge, failures, owner/action, limitations.
- Honest attribution and maturity labels.

## What remains separate

- Forecast models, ECL assumptions, pricing conventions and broker collateral policies.
- Each repository's code, installation, input schema, tests and release cycle.
- Human sample acceptance, model adoption and operational authorization.

There is no automatic pipeline from FCT to Workbench to ECL. The actual existing code reuse is the Workbench's pinned Model Risk Lab numerical kernel. File transfers and scope declarations require explicit human checks. Shared code is justified only by a common mathematical/input contract, never by both projects using the word risk.

## Placement and promotion

| Layer | Entry requirement | What does not qualify | Next improvement |
| --- | --- | --- | --- |
| Flagship | One target user and decision; runnable path; independent checks; findings and handoff; tested failure state | A list of calculators or a feature count | Independent first-use observation and repeat-task evidence |
| Specialist | One coherent technical question, reproducible evidence and its own limits | A broad label such as “all credit risk” | Deeper domain challenge and distinct user value |
| Lab | Reproducible teaching inputs and transparent assumptions | Claimed client experience or production calibration | Complete the exercise and defend a changed-input case |
| Reference/history | Source and contribution disclosed | Presenting forks/team work as sole-authored | Read selectively; retain provenance |

The flagship label indicates editorial priority, not institutional approval. Specialist status is also not a maturity grade. Every case keeps an explicit evidence boundary.

## Review acceptance

1. An unfamiliar reader identifies the user, question and expected handoff from the first page.
2. Instructions lead to the supplied evidence without private files or undocumented services.
3. A counterexample can change or constrain the recommendation.
4. Numeric checks do not silently grant sample acceptance or approve a model.
5. Every public repository has a primary placement; forks and the profile do not inflate model counts.
6. Learning gaps remain visible without occupying the main showcase.

Changing presentation does not justify rewriting working numerical engines. Future code integration needs its own input contract and validation.
